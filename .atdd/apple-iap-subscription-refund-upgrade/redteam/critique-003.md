# Critique Report: ADR-003

## 개요
- **ADR**: 003. 구독 상태 관리 아키텍처
- **검토 일시**: 2026-02-24 18:35
- **전체 위험도**: MEDIUM

---

## 이슈 목록

### [SEC-1] 이력 테이블 접근 제어
- **관점**: Security
- **심각도**: LOW
- **설명**: SubscriptionHistory 테이블에 사용자의 구독 이력이 모두 저장된다. 이 테이블에 대한 접근 제어가 언급되지 않았다.
- **영향**: 내부자에 의한 구독 정보 유출
- **제안**:
  - 이력 테이블에 대한 읽기 권한 최소화
  - 감사 로그 기록 (누가 언제 조회했는지)
  - PII 데이터 마스킹 고려

### [PERF-1] 이력 테이블 대용량화 쿼리 성능
- **관점**: Performance
- **심각도**: MEDIUM
- **설명**: 이력 테이블이 1억 건을 초과할 경우, 특정 구독의 이력 조회 쿼리 성능이 저하될 수 있다. 인덱싱 전략이 정의되지 않았다.
- **영향**: CS 대응 시 이력 조회 지연, 관리자 페이지 느려짐
- **제안**:
  - `subscription_id` + `created_at` 복합 인덱스 생성
  - 파티셔닝 전략 (월 단위 또는 분기 단위)
  - 아카이빙 전 구체적인 임계값 정의 (예: 5,000만 건)

### [SCALE-1] 낙관적 락 충돌 빈발 시 병목
- **관점**: Scalability
- **심각도**: MEDIUM
- **설명**: 낙관적 락 충돌율 5%를 재검토 조건으로 설정했으나, 실제로 5%가 넘는 상황에서 어떻게 대응할지가 불명확하다.
- **영향**: 높은 동시성에서 재시도 폭증, 처리 지연
- **제안**:
  - 충돌 시 재시도 횟수 제한 (예: 3회)
  - 재시도 실패 시 분산 락으로 전환 검토
  - 사용자별 직렬화 큐 적용 (ADR-002와 연계)

### [MAIN-1] 상태 전이 매트릭스 동기화
- **관점**: Maintainability
- **심각도**: MEDIUM
- **설명**: "상태 전이 매트릭스 문서화"를 완화 전략으로 제시했으나, 문서와 코드 간 동기화를 어떻게 보장할지가 정의되지 않았다.
- **영향**: 문서와 실제 코드의 불일치, 버그 유발
- **제안**:
  - 상태 전이 테스트 코드로 매트릭스 검증
  - 상태 전이 규칙을 Enum 또는 설정 파일로 외부화
  - CI에서 상태 전이 커버리지 측정

### [BIZ-1] 멱등성 구현 구체화 필요
- **관점**: Business
- **심각도**: HIGH
- **설명**: "Apple Webhook은 중복 발송 가능 (멱등성 필요)"라고 언급했으나, 구체적인 멱등성 구현 방식이 정의되지 않았다.
- **영향**: 중복 Webhook으로 인한 상태 오류, 잘못된 권한 부여/회수
- **제안**:
  - Webhook의 `transactionId` 또는 `signedDate` 기반 멱등성 키 사용
  - 이미 처리된 Webhook은 무시 (또는 동일 결과 반환)
  - Redis 또는 DB에 멱등성 키 저장 (TTL 24시간)

### [BIZ-2] Apple 이벤트 타입과 상태 전이 매핑
- **관점**: Business
- **심각도**: MEDIUM
- **설명**: Apple은 13개 이벤트 타입(SUBSCRIBED, DID_RENEW, REFUND 등)을 전송하는데, 각 이벤트가 어떤 상태 전이를 유발하는지 매핑이 정의되지 않았다.
- **영향**: 이벤트 처리 누락, 잘못된 상태 전이
- **제안**:
  - Apple 이벤트 타입별 상태 전이 매핑 테이블 작성
  - 정의되지 않은 이벤트에 대한 기본 처리 정책
  - 새로운 이벤트 타입 감지 시 알림

### [REL-1] 낙관적 락 재시도 실패 시나리오
- **관점**: Reliability
- **심각도**: MEDIUM
- **설명**: 높은 동시성에서 낙관적 락 재시도가 계속 실패할 경우에 대한 대응이 정의되지 않았다.
- **영향**: Webhook 처리 실패, 구독 상태 동기화 실패
- **제안**:
  - 최대 재시도 횟수 초과 시 DLQ로 이동
  - 수동 개입을 위한 알림 발송
  - 분산 락으로의 Fallback 전략
