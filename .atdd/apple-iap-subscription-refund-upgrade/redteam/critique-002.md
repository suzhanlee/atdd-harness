# Critique Report: ADR-002

## 개요
- **ADR**: 002. 비동기 메시지 처리 아키텍처 (RabbitMQ)
- **검토 일시**: 2026-02-24 18:35
- **전체 위험도**: MEDIUM

---

## 이슈 목록

### [SEC-1] 메시지 암호화 미언급
- **관점**: Security
- **심각도**: LOW
- **설명**: Webhook 메시지가 RabbitMQ를 통해 전달되는데, 메시지 암호화(TLS) 또는 메시지 레벨 암호화에 대한 언급이 없다.
- **영향**: 내부 네트워크에서 메시지 탈취 시 구독 정보 노출
- **제안**:
  - RabbitMQ 클러스터 간 TLS 연결 구성
  - 민감 정보(PII)는 메시지에서 제외하거나 암호화
  - VPC 내부 네트워크 격리 확인

### [PERF-1] 큐 적체 시 처리 지연
- **관점**: Performance
- **심각도**: MEDIUM
- **설명**: 컨슈머 처리 속도가 프로듀서를 따라가지 못하는 경우 큐에 메시지가 적체된다. "컨슈머 오토스케일링"을 완화 전략으로 제시했으나, 구체적인 스케일링 기준이 없다.
- **영향**: Webhook 처리 지연, Apple 재시도와 중복 처리 증가
- **제안**:
  - 큐 길이 기반 오토스케일링 임계값 정의 (예: 1,000개 초과 시 스케일 아웃)
  - 처리 지연 시간 모니터링 (예: 10초 초과 시 알림)
  - Prefetch count 조정으로 컨슈머 부하 분산

### [SCALE-1] Kafka 전환 비용
- **관점**: Scalability
- **심각도**: MEDIUM
- **설명**: 1,000 TPS 초과 시 Kafka 전환을 고려하나, 전환 비용과 마이그레이션 계획이 정의되지 않았다.
- **영향**: 트래픽 급증 시 즉각적인 대응 어려움
- **제안**:
  - Kafka 전환을 위한 사전 요구사항 정의
  - RabbitMQ 최대 처리량 벤치마킹 (실제 한계 파악)
  - 500 TPS 도달 시 Kafka PoC 시작 계획

### [MAIN-1] DLQ 모니터링 기준 미정의
- **관점**: Maintainability
- **심각도**: MEDIUM
- **설명**: "DLQ 무한 증가"를 위험으로 언급했으나, DLQ 모니터링 및 알림 기준이 구체적이지 않다.
- **영향**: 실패 메시지 파악 지연, CS 대응 늦어짐
- **제안**:
  - DLQ 크기 임계값 정의 (예: 100개 초과 시 Slack 알림)
  - DLQ 메시지 수명 주기 정의 (7일 후 자동 삭제?)
  - DLQ 대시보드 구성

### [BIZ-1] 사용자별 순서 보장 검증 필요
- **관점**: Business
- **심각도**: HIGH
- **설명**: "사용자 ID 기반 라우팅으로 단일 큐 처리"를 완화 전략으로 제시했으나, 이것이 실제로 RabbitMQ에서 어떻게 구현되는지가 불명확하다.
- **영향**: 같은 사용자의 구독 이벤트가 순서대로 처리되지 않아 상태 불일치 발생
- **제안**:
  - Single Active Consumer 패턴 검토
  - 사용자 ID 기반 Consistent Hashing Exchange 사용
  - 또는 단일 큐 + 사용자 ID 기반 순차 처리 로직 구현
  - 순서 보장 테스트 케이스 작성

### [BIZ-2] Apple 재시도와 큐 재시도 정책 충돌
- **관점**: Business
- **심각도**: MEDIUM
- **설명**: Apple은 Webhook 실패 시 재시도하며, 큐 내부에서도 재시도가 발생한다. 두 재시도 정책이 충돌할 수 있다.
- **영향**: 과도한 재시도로 인한 처리 폭증, 중복 처리
- **제안**:
  - Apple Webhook 수신 → 즉시 200 응답 (재시도 방지)
  - 큐 재시도는 최대 3회로 제한
  - Apple의 재시도 간격과 겹치지 않도록 지수 백오프 조정

### [REL-1] RabbitMQ 클러스터 장애 시 메시지 유실
- **관점**: Reliability
- **심각도**: HIGH
- **설명**: RabbitMQ 클러스터 전체 장애 시 큐에 있는 메시지가 유실될 수 있다. Quorum Queue가 아닌 Classic Queue를 사용하는 경우 특히 취약하다.
- **영향**: 처리되지 않은 Webhook 이벤트 영구 손실
- **제안**:
  - Quorum Queue 사용 (Raft 기반 복제)
  - 큐와 메시지의 내구성(Durable) 설정 확인
  - 다중 가용영역 클러스터 구성
  - 장애 시 Apple이 재시도하므로 최종 일관성 보장 (단, 재시도 횟수 제한 고려)

### [REL-2] 재처리 스케줄러 신뢰성
- **관점**: Reliability
- **심각도**: MEDIUM
- **설명**: DLQ 메시지를 재처리하는 스케줄러의 신뢰성이 보장되지 않는다. 스케줄러 자체가 장애 나면?
- **영향**: DLQ 메시지가 영구적으로 처리되지 않음
- **제안**:
  - 스케줄러 이중화 (Leader Election)
  - 재처리 실패 시 알림
  - 수동 재처리 API 제공

## 권장 사항

1. **[BIZ-1] 사용자별 순서 보장 구현 방식 명확화** (HIGH 우선순위)
   - RabbitMQ에서 순서 보장을 위한 구체적인 구현 방식 결정
   - Single Active Consumer 또는 Consistent Hashing Exchange 선택

2. **[REL-1] Quorum Queue 사용** (HIGH 우선순위)
   - 메시지 유실 방지를 위해 Quorum Queue로 전환
   - 다중 노드 클러스터 구성

3. **[BIZ-2] 재시도 정책 통합** (MEDIUM 우선순위)
   - Apple 재시도와 내부 재시도 정책의 조율
   - Webhook 수신 즉시 200 응답 정책 명시

4. **[PERF-1] 오토스케일링 기준 정의** (MEDIUM 우선순위)
   - 구체적인 큐 길이 및 지연 시간 임계값 설정
