## Pre-Mortem (Phase A 결과)

### Q1: 이 결정이 1년 후 실패한다면 가장 가능성 높은 이유는?
1. **서버 장애 시 이벤트 유실**: 메시지 브로커 장애로 Webhook 이벤트 손실
2. **처리 지연 누적**: 컨슈머 처리 속도가 프로듀서 속도를 따라가지 못해 큐 적체
3. **DLQ 관리 실패**: 실패 메시지가 DLQ에 쌓여만 가고 재처리되지 않음

### Q2: 실패 당시 상황
| 항목 | 현재 | 실패 시나리오 |
|------|------|---------------|
| 트래픽 | 100 TPS | 1,000 TPS (이벤트 폭증) |
| 팀 규모 | 2명 | 5명 |
| 데이터 크기 | 10GB | 1TB |
| 비즈니스 | 초기 서비스 | 블랙프라이데이 프로모션 |

### Q3: 미리 알았다면 다른 선택
- 만약 **메시지 순서 보장이 중요**했다는 것을 알았다면 → Kafka를 고려했을 것
- 만약 **운영 복잡도를 최소화**해야 한다는 것을 알았다면 → SQS 같은 Managed Service를 고려했을 것

## Context

Apple Webhook은 구독 상태 변경 이벤트를 실시간으로 전달한다. 동기식 처리는 서버 장애 시 이벤트 유실 위험이 있어 비동기 메시지 처리 아키텍처가 필요하다.

### 비즈니스 요구사항
- 서버 장애 시에도 이벤트 유실 방지
- 이벤트 처리 순서 보장 (같은 사용자 내)
- 처리 실패 시 재시도 및 복구 메커니즘

### 기술적 제약사항
- Apple은 Webhook 수신 시 500ms 이내 응답 기대
- 실패 시 Apple이 재시도하나, 재시도 횟수 제한 있음
- 기존 인프라에 RabbitMQ 운영 경험 있음

### 팀/조직 상황
- Kafka 운영 경험 없음
- RabbitMQ 운영 노하우 보유
- Spring AMQP 숙련도 높음

---

## Decision

1. **메시지 브로커**: RabbitMQ 사용
2. **처리 흐름**: Webhook 수신 → 큐 적재 → 즉시 200 응답 → 컨슈머 비동기 처리
3. **장애 대응**: DLQ(Dead Letter Queue) + 재처리 스케줄러
4. **사용자별 순서 보장**: Consistent Hashing Exchange로 사용자 ID 기반 라우팅
5. **재시도 정책 통합**:
   - Webhook 수신 즉시 200 응답 (Apple 재시도 방지)
   - 큐 내부 재시도: 최대 3회, 지수 백오프 (1s, 5s, 30s)

### 선택 설명 (트레이드오프)
RabbitMQ를 선택한 이유:
- **팀 친숙도 최우선**: Kafka 러닝커브 없이 즉시 개발 가능
- **비용 효율성**: 기존 인프라 활용으로 추가 비용 없음
- **적합한 트래픽 규모**: 현재 100 TPS에서 충분한 성능

Kafka는 높은 처리량과 순서 보장이 우수하지만, 현재 요구사항에 과도한 엔지니어링. SQS는 운영 편의성이 높으나 AWS 종속성과 비용 증가 우려.

## Alternatives Considered

### RabbitMQ (선택)
- **장점**:
  - 팀 운영 경험 풍부
  - 유연한 라우팅 (Exchange/Queue)
  - DLQ 내장 지원
  - 낮은 운영 비용
- **단점**:
  - 클러스터링 복잡도
  - 메시지 순서 보장 파티션 단위
- **실패 시나리오**: 큐 적체 시 메모리 부족으로 장애

### Apache Kafka
- **장점**:
  - 높은 처리량 (수십만 TPS)
  - 강력한 순서 보장
  - 메시지 영속성
  - 이벤트 소싱 지원
- **단점**:
  - 높은 운영 복잡도 (Zookeeper/KRaft)
  - 팀 러닝커브
  - 리소스 요구사항 높음
- **선택하지 않은 이유**: 현재 규모에 과도한 엔지니어링
- **실패 시나리오**: 운영 미숙으로 장애 대응 실패

### AWS SQS
- **장점**:
  - 완전 관리형 서비스
  - 무제한 확장
  - DLQ 지원
- **단점**:
  - AWS 종속성
  - 메시지 순서 보장 제한 (FIFO 큐 필요)
  - 지연 시간 (폴링 방식)
  - 비용 증가
- **선택하지 않은 이유**: 기존 인프라와의 일관성, 비용
- **실패 시나리오**: AWS 리전 장애 시 서비스 중단

## Consequences

### 긍정적
- 서버 장애 시에도 메시지 유실 방지
- Webhook 응답 시간 단축 (큐 적재 후 즉시 응답)
- 기존 팀 역량 활용으로 빠른 개발
- 낮은 운영 비용

### 부정적
- 메시지 처리 지연 가능성 (큐 대기 시간)
- RabbitMQ 클러스터 운영 부담
- 모니터링 및 알림 구축 필요

### 위험
- **큐 적체**: 컨슈머 처리 속도가 프로듀서를 따라가지 못함
  - 완화 전략: 컨슈머 오토스케일링, 큐 길이 모니터링
- **DLQ 무한 증가**: 실패 메시지가 계속 쌓임
  - 완화 전략: 재처리 스케줄러, 최대 재시도 횟수 제한
- **메시지 순서**: 같은 사용자의 이벤트가 순서대로 처리되지 않을 수 있음
  - 완화 전략: 사용자 ID 기반 라우팅으로 단일 큐 처리
